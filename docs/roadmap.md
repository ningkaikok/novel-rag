# 项目路线图

路线图按“先建立可评测闭环，再增加能力”的顺序排列。每个里程碑只有满足验收标准
才算完成；未进入当前里程碑的功能不提前引入依赖。M3.3～M3.6 依次补齐索引质量、
检索实验、答案忠实度和多轮上下文边界，再进入 M4 关系图质量和 M5/M6 生产化边界。

## M3.3：索引质量与数据血缘（已完成，P0）

先保证“进入数据库的内容就是模型实际处理过的内容”。这一阶段只处理离线索引，不增加
Agent 框架，也不改变在线召回策略。质量检查必须针对最终送入 embedding 的文本，而不是
只看原始 chunk 的字符数；开启 Contextual Retrieval 或建立层级摘要后，同样需要检查拼接
上下文和摘要节点的真实输入。

- [x] 增加可独立运行的索引质量报告，记录解码方式、解析异常、替换/控制字符、空片段、
  精确重复片段、章节识别情况、每本书 chunk 数量与长度分布
- [x] 使用当前 embedding 模型的真实 tokenizer 和最大序列长度，统计最终输入 token 的
  P50/P95/最大值以及被截断数量；不再用字符数或 BM25 分词数代替模型 token
- [x] 建立硬性闸门：空 embedding 输入、静默截断、非有限向量或向量维度不一致时停止
  当前书的原子替换；章节识别率、疑似乱码和重复率先作为报告警告，避免误伤无标题小说
- [x] 复用并补齐现有文件 SHA-256 和索引配置指纹，报告数据源哈希、embedding 模型、
  tokenizer/最大长度、chunk/overlap、上下文配置和生成时间，使结果可以追溯和复现
- [x] 为普通片段、上下文增强片段、章节摘要和全书摘要补充单元测试，至少覆盖“原文未
  超长但拼接上下文后超长”、空书、异常向量和任务失败不替换旧索引

验收：命令行能为每本书生成结构化报告；所有实际 embedding 输入都经过同一个 tokenizer
检查；硬性错误不会替换可用旧索引；同一文件和配置能够得到相同的数据源/管道指纹。

实现状态：质量报告和 tokenizer 门禁已接入 `src/ingest.py`，报告摘要保存到
`index_manifest.quality_report`；`scripts/check_index_quality.py` 可在写库前执行预检。
已在本机 PostgreSQL 上完成旧表补列和 4 本书的真实索引迁移，共 33,536 个片段全部通过
质量门禁；第二次同步确认 4 本书均为未变化。层级摘要中曾发现的 2,453 个超长输入已
改为按真实 tokenizer 显式压缩到 512 tokens，不再依赖模型静默截断。

## M3.4：检索实验与失败策略（后续阶段，P1～P2）

索引输入可信后，再用固定评测集决定 embedding 和 chunk 参数，并为确实缺少证据的查询
设计有边界的补救。向量、BM25、层级导航、RRF 和重排已经是标准主链路，不把它们重复
包装成“失败后切换”的降级路径。

- [ ] 建立可复现的评测矩阵，对比 embedding 模型、chunk size、overlap 和上下文增强，
  记录配置指纹、Recall@K、MRR/nDCG、索引耗时、查询延迟、内存与向量存储成本
- [ ] 实验使用受控样本和临时索引/独立命名空间，不覆盖当前可用索引；报告逐条展示相对
  基线的新增命中和回退案例，而不只给出平均分
- [ ] 定义可解释的低置信度信号，例如候选分数/排名差距、实体覆盖、跨书分散程度和证据
  覆盖不足；先通过离线失败集校准，不直接把不同检索器的原始分数混成统一阈值
- [ ] 第一版只允许一次有边界的补救，例如查询扩展后重新检索；仍无证据时请求澄清或
  明确拒答，并把触发条件、额外耗时和最终路径写入现有检索 trace

验收：同一评测配置可重复运行且不污染正式索引；候选在哪一步丢失可以逐条解释；低置信
度查询最多触发一次补救，仍无可靠证据时不会交给模型自由编造。

## M3.5：引用忠实度与运行追踪（后续阶段，P3～P4）

最后验证“检索到的证据是否真的支持答案”。先离线标注和影子评测，再决定是否影响用户
回答，避免中文小说中的隐喻、指代和人物动机被不稳定的 NLI/LLM Judge 误判。

- [ ] 将引用质量拆成引用正确性（编号有效）、引用完整性（事实陈述是否有引用）和引用
  忠实度（原文是否支持陈述），保留现有编号/关键词检查作为基线
- [ ] 建立人工标注的小型陈述—证据集，对比规则、NLI 或 LLM Judge；第一阶段只记录
  影子结果和误判，不阻止回答，达到明确阈值后再逐步启用“不确定”提示或拒答
- [ ] 明确 `request_id`、`run_id`、`trace_id` 的职责：HTTP 请求继续使用现有
  `request_id`；出现重试、Agent 多步或后台执行后，再用 `run_id` 串联一次逻辑运行，
  `trace_id` 留给跨服务观测
- [ ] 在现有 trace 中补齐在线配置版本，包括 reranker、生成模型、Prompt/路由策略和
  最终状态；日志不保存 API Key、完整版权原文或不必要的用户隐私

验收：引用三类指标可以分别计算；影子评测能展示自动判断与人工标签的差异；一次回答可
关联到使用的数据源/索引配置和在线模型配置；在没有可靠阈值前不会因自动支持度误判而
静默删除正确回答。

## M3.6：多轮上下文与记忆边界（规划中，P2～P3）

当前项目**暂不引入完整对话压缩**：普通问答的最终 Prompt 只包含当前问题和检索证据，
历史主要用于查询改写；查询改写只读取最近 4 轮、每条最多 200 字的截断历史。这样可以
避免把尚未验证的摘要逻辑提前放进主链路，也不会为短会话增加额外 LLM 调用。

只有出现以下信号之一，才启动本阶段：会话超过 10～20 轮、改写 Prompt 经常超过
2K～4K token、用户需要跨多轮记住人物/书名/已确认事实，或最终回答开始正式携带历史上下文。

- [ ] 建立多轮评测集，覆盖指代、否定、时间顺序、跨书切换和“纠正上一轮”的场景
- [ ] 增加 token 预算与可观测字段，记录历史长度、改写耗时、摘要耗时和截断原因
- [ ] 引入滚动会话摘要，只在超过阈值时更新；摘要失败时保留最近原文，不阻塞回答
- [ ] 保留最近 4～6 轮原文，并增加结构化事实记忆（人物、书名、用户已确认结论）
- [ ] 最终上下文采用“会话摘要 + 最近对话 + 当前检索证据”，而不是把完整历史全部拼入
- [ ] 增加摘要漂移、事实丢失和跨轮引用错误的回归测试；未经评测不得默认影响回答

推荐顺序：先完成查询改写评测，再增加 token 预算和滚动摘要，最后再接入结构化事实记忆。
摘要不能替代原文证据；涉及小说事实时，仍必须回到当前检索结果进行引用和核验。

阶段性验收：短会话路径不增加额外模型调用；长会话的 Prompt 在预算内；摘要失败可降级到
最近原文；人物、否定关系和时间顺序在评测集上没有明显回退；每次压缩都能在 trace 中解释。

M3.3～M3.6 优先复用现有的 [检索可视化评测](retrieval-observability.md)、
[章节与引用评测](citations-and-chapters.md) 和 `scripts/eval_retrieval.py`。这一轮不提前引入
独立向量数据库、消息队列、微服务或 LangGraph。

## M6：Agent 平台化与生产边界（规划中）

这一阶段不是立刻引入一整套微服务，而是把当前 Agent Lab 的五个只读工具逐步拆成可
注册、可授权、可观测、可恢复的边界。先用普通 Python 保持学习链路透明，再按真实
需求评估 MCP、OpenTelemetry 和 LangGraph。

- [ ] M6.1：建立轻量 Control Plane，用统一 `ToolSpec` / Tool Registry 管理 schema、版本、
  权限、风险等级、超时和启停；运行时只读取经过验证的不可变快照
- [ ] M6.2：增加 Tool Gateway，集中做鉴权、参数校验、出站白名单、Prompt Injection
  隔离、限流、超时、幂等、分类重试、熔断和审计
- [ ] M6.3：增加 Model Gateway，统一 Ollama、Claude 和智谱适配，记录 token/耗时/成本，
  支持按任务选模、预算上限、超时和显式降级
- [ ] M6.4：统一 Agent 事件，串起 Router、Planner、Tool、检索、LLM 和 SSE 的 `run_id`；
  同时建立路由准确率、工具成功率、答案依据率、延迟和成本的评测闭环
- [ ] M6.5：拆分 Chat History、Run State 和 Event Log；短问答继续 SSE，长任务改为
  `job_id + worker`，并补 checkpoint、幂等、取消、恢复和死信处理
- [ ] M6.6：在工具需要跨客户端复用时增加 MCP 适配，不绕过内部权限和审计边界
- [ ] M6.7：结合 M5 完成租户隔离、配额、数据保留/删除、备份、结构化日志、监控告警
  和灰度发布；高风险写工具默认需要人工审批

阶段性验收：五个现有工具都从统一 Gateway 执行；外部文本中的指令不能越权触发工具；
一次 Agent 运行可以按 `run_id` 还原完整事件顺序并计算质量、延迟和成本指标；权限错误、
参数错误、超时和下游失败可区分；恢复任务不会重复执行有副作用的工具；模型供应商失败
时按显式策略降级而不是静默换模型。只有在出现跨进程恢复、人工审批、复杂分支或长任务
时，才把已测试的编排函数迁入 LangGraph。

架构边界和迁移示例见 [Agent 平台化架构](agent-platform-architecture.md)。

## 暂不进入路线图主干

- **LangGraph**：M6.5 之前不引入；已有五步教学工具循环仍用普通 Python，等需要人工
  暂停恢复、跨进程检查点、并行分支或更复杂重试时再复审。
- **多 Agent**：没有评测证明单流水线无法解决之前不增加。
- **更换向量数据库/搜索引擎**：先用 PostgreSQL 把检索和产品闭环做完整。

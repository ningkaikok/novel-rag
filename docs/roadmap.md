# 项目路线图

路线图按“先建立可评测闭环，再增加能力”的顺序排列。每个里程碑只有满足验收标准
才算完成；未进入当前里程碑的功能不提前引入依赖。M3.3～M3.6 依次补齐索引质量、
工程加固、检索实验、答案忠实度和多轮上下文边界，再进入 M4 关系图质量和 M5/M6
生产化边界。M3.2.1（Agent 循环的动作协议）是 M3.2 的加固项，与检索主链路正交，
按埋点测出的真实失败率插队。

## M3.2.1：Agent 循环的动作协议（规划中，P2）

M3.2 的验收标准是“初学者能直接看到 观察 → 选择工具 → 获得结果 → 继续判断”，前端按 SSE 逐步展示。
但当前的动作解析是**先收完整段 JSON 再解析**（`src/agent_lab.py` 的 `_parse_action`：剥掉 json
围栏后 `json.loads`，失败再用正则抓第一个 `{...}`）。这带来三个结构性限制：

- **不能流式**。JSON 必须收完才能解析，所以“模型正在选哪个工具”只有整段生成结束才知道，
  逐步展示的粒度被卡在“每步一次”，而不是“每步之内也可见”。这恰好削弱了 M3.2 的核心卖点。
- **降级路径是猜**。剥围栏 + 正则抓第一个花括号，模型在 JSON 前后多写一句话就可能抓错对象。
- **解析失败没有回路**。`json.JSONDecodeError` 之后是兜底或异常，而不是“告诉模型它违反了协议、
  把错误回灌进对话再来一轮”。LLM 输出不合规是常态而非异常，当前按异常处理。

改法是把动作从 JSON 换成**首行标签协议**：要求回复第一行只有 THINK / TOOL / FINISH 之一
（双反引号包裹），正文跟在后面。第一个 chunk 就能判定这段文本该进“思考”面板还是“答案”区；
解析在前 64 字符内完成，容忍反引号数量变化和裸标签写法。配套三件事：

- [ ] 协议违规不抛异常：生成一条修复消息回灌进对话并重试本轮，重试次数计入步数预算
- [ ] 步数预算耗尽时统一强制收尾（当前是 `if step == max_steps and source_registry:` 一个特殊分支），
      保证任何情况下都不会留下半截回答
- [ ] 标签解析、违规分类和修复消息拼装抽成独立模块并单测，与工具循环本身解耦

不改的部分：现有的重复动作保护（`signature = json.dumps([tool, args], sort_keys=True)`）、
只读白名单、无证据拒答和 3～5 步上限全部保留。这次只换“模型如何表达下一步动作”这一层。

验收：工具选择在首个 chunk 就能路由到对应面板；构造一个必然违反协议的模型输出，循环能回灌修复
并在预算内正常收尾，而不是抛异常或静默兜底。

> 优先级 P2，且**先埋点再排期**：当前 JSON 动作解析在自家模型上的真实失败率还没测过。
> 先加一条“动作解析失败/走正则兜底”的计数埋点，用真实失败率决定这件事排在 M3.4 之前还是之后，
> 不要凭“这个设计更好”就抢跑——这与本路线图对 T0 渲染通道、多小问的处理方式一致。
>
> **埋点已完成（2026-09-05）**，上面三项仍待真实数据决定排期。每个由规划器产出的步骤
> 都带 `parse_mode`（`strict` / `fenced` / `regex` / `failed:<类别>`）并随 `agent_steps`
> 落库，用 `uv run python scripts/agent_parse_stats.py` 聚合。规划器没参与的步骤
> （最后一步强制收尾）记 None，不进分母；动作被目录门禁换掉的步骤**仍然计入**——
> 埋点问的是"解析多久失败一次"，不是"这个动作最后有没有被采用"。
>
> 判读口径：`regex + failed` 合计 <2% 说明当前协议够用、本项继续后置；>10% 说明步数
> 预算正在被解析问题稳定吃掉，值得提前。其中 **`regex` 比 `failed` 更值得警惕**——
> 它是"成功了但成功得可疑"：正则抓第一个花括号，抓错了不报错，会静默执行一个错误
> 的动作；`failed` 至少还会走降级并在界面上写明原因。
> 与 M6.1 的关系：M6.1 管的是**工具契约**（ToolSpec / ToolResult），本项管的是**动作协议**
> （模型如何声明下一步）。两者正交，互不为前置。

## M3.3：索引质量与数据血缘（已完成，P0）

先保证“进入数据库的内容就是模型实际处理过的内容”。这一阶段只处理离线索引，不增加
Agent 框架，也不改变在线召回策略。质量检查必须针对最终送入 embedding 的文本，而不是
只看原始 chunk 的字符数；开启 Contextual Retrieval 或建立层级摘要后，同样需要检查拼接
上下文和摘要节点的真实输入。

- [x] 增加可独立运行的索引质量报告，记录解码方式、解析异常、替换/控制字符、空片段、
  精确重复片段、章节识别情况、每本书 chunk 数量与长度分布
- [x] 使用当前 embedding 模型的真实 tokenizer 和最大序列长度，统计最终输入 token 的
  P50/P95/最大值以及被截断数量；不再用字符数或 BM25 分词数代替模型 token
- [x] 建立硬性闸门：空 embedding 输入、静默截断、非有限向量或向量维度不一致时停止
  当前书的原子替换；章节识别率、疑似乱码和重复率先作为报告警告，避免误伤无标题小说
- [x] 复用并补齐现有文件 SHA-256 和索引配置指纹，报告数据源哈希、embedding 模型、
  tokenizer/最大长度、chunk/overlap、上下文配置和生成时间，使结果可以追溯和复现
- [x] 为普通片段、上下文增强片段、章节摘要和全书摘要补充单元测试，至少覆盖“原文未
  超长但拼接上下文后超长”、空书、异常向量和任务失败不替换旧索引

验收：命令行能为每本书生成结构化报告；所有实际 embedding 输入都经过同一个 tokenizer
检查；硬性错误不会替换可用旧索引；同一文件和配置能够得到相同的数据源/管道指纹。

实现状态：质量报告和 tokenizer 门禁已接入 `src/ingest.py`，报告摘要保存到
`index_manifest.quality_report`；`scripts/check_index_quality.py` 可在写库前执行预检。
已在本机 PostgreSQL 上完成旧表补列和 4 本书的真实索引迁移，共 33,536 个片段全部通过
质量门禁；第二次同步确认 4 本书均为未变化。层级摘要中曾发现的 2,453 个超长输入已
改为按真实 tokenizer 显式压缩到 512 tokens，不再依赖模型静默截断。

## M3.4：检索实验与失败策略（后续阶段，P1～P2）

索引输入可信后，再用固定评测集决定 embedding 和 chunk 参数，并为确实缺少证据的查询
设计有边界的补救。向量、BM25、层级导航、RRF 和重排已经是标准主链路，不把它们重复
包装成“失败后切换”的降级路径。

- [x] 建立可复现的评测矩阵，对比 embedding 模型、chunk size、overlap 和上下文增强，
  记录配置指纹、Recall@K、MRR/nDCG、索引耗时、查询延迟、内存与向量存储成本
  （`scripts/eval_matrix.py`：隔离临时库 + 配置指纹 + 成本记录；第一轮实验结论见
  [docs/experiments/m34-retrieval-matrix.md](experiments/m34-retrieval-matrix.md)）
- [x] Contextual Retrieval 改为 `auto` 成本分级，而不是简单改默认开关：实测单条约
  4.4 秒、超过 2000 片段的书目前直接跳过（见 `src/config.py`）。分级策略——小体量书
  默认后台构建；大部头默认跳过或只处理低上下文质量片段；结果按内容哈希缓存；只有
  本项目评测集证明 Recall/MRR 明显提升才扩大范围。`CONTEXTUAL_MODE=off/auto/on`
  三档，auto 档还要求生成后端可用，避免制造整页失败日志
- [x] **性能预算与延迟排查（P2）**：大部头实测单次混合检索 2.3~3.3s（见
  [实验报告](experiments/m34-retrieval-matrix.md)）。用 M3.1 trace 的分阶段耗时
  定位瓶颈占比（embedding 编码 / HNSW 召回 / BM25 / RRF / 重排），产出延迟画像
  报告；只对"占比最大且修复成本低"的环节做优化，优化前后必须过夜间评测门禁
  （已完成：精排占 51%、BM25 占 30% 且 EXPLAIN 实锤全量聚合问题，
  见 [延迟画像](experiments/m34-latency-profile.md)；两条优化项见下）
- [x] BM25 两阶段聚合改写（2026-08-23）：SQL 内每词按 tf 取 Top-N
  （LATERAL 子查询 + `(term, tf DESC, novel, chunk_id)` 复合索引提前终止扫描，
  `BM25_PER_TERM_LIMIT` 可调）、Python 端融合打分，替代「聚合全部命中行再排序」；
  实测《凡人修仙传》真实库 BM25 阶段 P50 227ms → **46ms**、均值 287ms → 71ms、
  P95 602ms → 215ms（EXPLAIN：常见词场景从堆扫描 15,636 行排序降到每词 ~0.6ms）；
  夜间检索门禁指标与基线持平（Recall@1 0.8 / Recall@3 1.0 / MRR 0.9），真实库
  13 条评测集与旧实现逐用例等价。语义近似 trade-off 与参数化逃生门见
  `keyword_retrieve` docstring
- [x] 重排候选数/批量调优实验（2026-08-25）：`RERANK_CANDIDATE_MULTIPLIER ∈ {2,3,4,6}`
  质量×延迟对照——机制上先确认实际候选数 = max(top_k × 倍数, RECALL_K)，生产路径
  （TOP_K=3）四档全被 `RECALL_K=20` 兜底为同一 20 候选池、精排 P50 370~420ms 无差异；
  multiplier 真正生效的大部头评测路径（top_k=20，池 40/60/80/120）实测每 +20 候选
  约 +300ms、质量非单调（m=2 与默认 m=3 全部用例等价，m≥4 recall@1 0.538→0.462
  回退）；批大小探针显示默认 batch_size=32 与最优差 <1%。结论：默认值 3 已在安全区
  （2~3），不改；生产精排延迟的进一步优化（RECALL_K 下限/设备/更小模型）另行立项

  澄清或明确拒答。不对所有问题默认做多查询扩展，避免模型调用、语义漂移和无谓延迟；
  触发条件、额外耗时和最终路径写入现有检索 trace（`QUERY_EXPAND_ENABLED` 默认关闭）

验收：同一评测配置可重复运行且不污染正式索引；候选在哪一步丢失可以逐条解释；低置信
度查询最多触发一次补救，仍无可靠证据时不会交给模型自由编造。

## M3.5：引用忠实度与运行追踪（后续阶段，P3～P4）

回答，避免中文小说中的隐喻、指代和人物动机被不稳定的 NLI/LLM Judge 误判。

- [x] 将引用质量拆成引用正确性（编号有效）、引用完整性（事实陈述是否有引用）和引用
  忠实度（原文是否支持陈述），保留现有编号/关键词检查作为基线
  （`src/citation_eval.py`：正确性沿用 `valid_number_ratio`；完整性新增
  `completeness` 分组，按句末标点分句并用可配置豁免词表跳过寒暄/元描述句；
  忠实度提供 `judge_support` 影子接口，依赖注入生成函数，只在评测脚本调用）
- [x] 建立人工标注的小型陈述—证据集，对比规则、NLI 或 LLM Judge；第一阶段只记录
  影子结果和误判，不阻止回答，达到明确阈值后再逐步启用“不确定”提示或拒答
  （`tests/citation_shadow_set.json` 53 条，证据全部取自仓库原创语料，第二批
  x2_ 前缀补齐否定关系/跨句/多跳/范围篡改/代词链五类；
  `scripts/eval_faithfulness_shadow.py` 输出各方法混淆矩阵、跨方法汇总指标与
  分歧样本，`--model` 可重复传入做多 Judge 对比，默认零成本只跑规则基线）
- [x] 明确 `request_id`、`run_id`、`trace_id` 的职责：HTTP 请求继续使用现有

## M3.6：多轮上下文与记忆边界（已完成，2026-09-05）

启动前的状态是：最终 Prompt 只包含当前问题和检索证据，历史仅用于查询改写，
因此"再展开讲讲""你刚才说的第二点"这类追问必然失效。七项全部完成，按依赖
顺序落地：

1. **多轮评测集先行**（2026-09-05）：`tests/multiturn_test_set.json`（22 条）+
   `scripts/eval_multiturn.py`，断言为确定性字符串包含/排除，不引入 LLM 评委。
   评测立刻测出一个比"没有记忆"更严重的存量 bug——改写会把用户亲口写出的主语
   替换成上文里更显眼的人名，也就是**悄悄回答另一个问题**。修复后 81.8% → 90.9%，
   见 [多轮改写评测](experiments/m36-multiturn-rewrite.md)
2. **回答 Prompt 正式携带历史**（2026-09-05）：`build_prompt(..., history=...)` 走
   带「对话背景」段的模板（`PROMPT_TEMPLATE_VERSION` v1 → v2），并用三条硬约束
   把背景压到最低地位——**不能当事实依据、不能被引用、与原文冲突时以原文为准**。
   这是本阶段风险最高的一处：模型一旦拿历史当依据，回答里的 [n] 就不再对应真实
   片段，引用可核验性会被直接破坏。预算裁剪（轮数 → 单轮字数 → 整轮丢弃）的每
   一步都写进 trace 的「对话背景」步骤，界面上能看到带了几轮、丢了什么、为什么丢。
   历史仍是**可选参数**：自由问答、Agent Lab、评测脚本都不传，行为与改造前一致

- [x] **工具输出的 token 预算闸**（2026-09-05：`AGENT_TOOL_MAX_CHARS`，默认 6000 字。
      第一道闸此前已有——`radius`≤3 / `limit`≤12 限制「取几段」；补上的是第二道——
      读到内容之后限制「多少字」。`read_neighbors` 中心片段无条件保留、向两侧对称
      生长，`get_chapter` 从末尾丢，截断原因写进规划器读得到的 observation。
      目录行同理按字数收窄，但 `facts["items"]` 保持完整——目录类确定性回答依赖它。
      用字数而不是 token：这份预算保护的是生成 prompt，而三个生成后端各有各的
      tokenizer。这与会话历史压缩是两件事，但同属上下文预算）
- [x] 建立多轮评测集，覆盖指代、否定、时间顺序、跨书切换和“纠正上一轮”的场景
      （2026-09-05：22 条 + `scripts/eval_multiturn.py`，并借此修掉改写偷换主语的 bug）
- [x] 增加 token 预算与可观测字段，记录历史长度、改写耗时、摘要耗时和截断原因
      （2026-09-05：历史长度、带入轮数、截断原因和摘要耗时都写进 trace 的「对话背景」步骤）
- [x] 引入滚动会话摘要，只在超过阈值时更新；摘要失败时保留最近原文，不阻塞回答
      （2026-09-05：`src/session_summary.py`；长会话评测集已补齐——
      `tests/session_summary_test_set.json`（6 条）+ `scripts/eval_session_summary.py`，
      两个模型（`glm:glm-4-flash`/`claude:haiku`）均 6/6 通过、零摘要漂移，达到
      开启标准，**`HISTORY_SUMMARY_ENABLED` 默认值已改为 `1`**（样本量仍有限，
      仅 3 篇短篇原创语料，未覆盖多轮滚动更新下的累积误差，详见
      [滚动会话摘要](experiments/m36-session-summary.md)）
- [x] 保留最近 4～6 轮原文，并增加结构化事实记忆（人物、书名、用户已确认结论）
      （2026-09-05：`HISTORY_MAX_TURNS` 默认 6；结构化事实记忆见
      `src/session_facts.py`——**只覆盖书名 + 人物，不做"用户已确认结论"**：
      唯一能确定信号强度的确认渠道是引用核实功能，覆盖面太窄；关键词猜测确认
      信号本身模糊，容易把反驳误判成确认，比不做还危险，留到有更可靠信号时再补。
      书名来自这一轮真实检索到的证据（`turn["sources"]`），人物名来自人物关系图
      的人名反查，**不调用任何模型**，因此不像滚动摘要那样需要开关，默认随对话
      背景生效；容量超限按"牺牲最旧提到的"原则丢弃，与逐字历史同一套策略）
- [x] 最终上下文采用“会话摘要 + 最近对话 + 当前检索证据”，而不是把完整历史全部拼入
      （2026-09-05：`build_history_block` + `PROMPT_TEMPLATE_WITH_HISTORY` 就是这个三段结构，
      且摘要与逐字历史分别标注，可信度不同）
- [x] 增加摘要漂移、事实丢失和跨轮引用错误的回归测试；未经评测不得默认影响回答
      （2026-09-05：`tests/backend/test_session_summary.py`，17 条按这三类组织；
      跨轮引用错误改成机械防线——背景段里的 `[n]` 一律抹掉，不靠提示词约束）

推荐顺序：先完成查询改写评测，再增加 token 预算和滚动摘要，最后再接入结构化事实记忆。
摘要不能替代原文证据；涉及小说事实时，仍必须回到当前检索结果进行引用和核验。

阶段性验收：短会话路径不增加额外模型调用；长会话的 Prompt 在预算内；摘要失败可降级到
最近原文；人物、否定关系和时间顺序在评测集上没有明显回退；每次压缩都能在 trace 中解释。

M3.3～M3.6 优先复用现有的 [检索可视化评测](retrieval-observability.md)、
[章节与引用评测](citations-and-chapters.md) 和 `scripts/eval_retrieval.py`。这一轮不提前引入
独立向量数据库、消息队列、微服务或 LangGraph。

  “先用 PostgreSQL 把检索和产品闭环做完整”，M3.4 的 BGE-M3 对照是**实验**不是长期共存，

- **下一问预取（next-turn prefetch）**：预测用户追问并提前检索会带来大量从未被使用

  只有真实日志证明追问模式高度可预测时再研究。注意与 Google Speculative RAG
  （小模型生成草稿、大模型验证，arXiv:2407.08223）是不同概念，后者如要实验也需
  先过成本评测。

## 0. 检索评测：一切改进的前提

### 为什么先做这个

改检索策略时最容易骗自己：随手试两个问题，感觉"好像变好了"，就认为成功了。
但检索是统计问题——一个改动完全可能让 A 类问题变好、同时让 B 类问题变差，
只试几个问题根本看不出来。

业界的经验数据是：**RAG 失败时，约七成的失败点在检索环节，不是生成环节**。
所以检索指标是最该先立起来的东西。

### 指标怎么定义的

理想做法是人工标注"每个问题的答案在哪几个片段里"，但工作量很大。这里用一个
更省事、但足够有效的**代理指标**：

> 对每个问题标注一组「正确答案的原文里必然出现的词」。比如问韩立的绰号，
> 答案原文里必然有「二愣子」三个字。某个被召回的片段包含任一期望关键词，
> 就算命中。

**局限要说清楚**：它只能证明"召回了含答案的片段"，不能证明"模型会用好它"；
片段里出现关键词也可能只是碰巧提到。但它有个决定性优点——**完全客观、可自动
重复跑**，对"比较改动前后哪个更好"这个用途足够了。

### 两个指标各自回答什么问题

| 指标 | 回答什么 | 为什么重要 |
| --- | --- | --- |
| **Recall@k** | 前 k 个结果里有没有至少一个命中 | 及格线。找不到，后面全免谈 |
| **MRR** | 第一个命中的排第几（取倒数再平均） | 最终只有 top-k 会进 prompt。**排在第 20 名的正确片段，实际效果等同于没找到** |

MRR 的计算方式：排第 1 得 1.0，排第 2 得 0.5，排第 10 得 0.1，完全没命中记 0
（不是跳过——跳过会让"召回率低但命中的都排第一"的系统拿到虚高分数）。

**两个指标要一起看**：`Recall@20` 高但 `MRR` 低，说明"东西在候选池里但排序很差"
——这正是[重排](#2-重排reranker)要解决的问题，而不是召回的问题。

### 测试集怎么设计的

难度是**故意拉开**的，用关键词在语料里的出现次数来控制：

| 难度 | 例子 | 出现次数 | 考什么 |
| --- | --- | --- | --- |
| hard | 窝头 | 1 次 | 极稀有词，语义检索几乎必然失败 |
| hard | 二愣子 | 3 次 | 稀有词 + 《降龙》里有同名干扰项 |
| hard | 韩铸 | 4 次 | 稀有人名 |
| medium | 长春功 | 63 次 | 常规专有名词 |
| easy | 塔罗会 | 661 次 | 高频词，兜底哨兵 |

还有几条用例**故意不参与检索评测**（`retrieval` 字段为 `null`，并写明原因）：

- **抗幻觉题**（"有没有提到哈利·波特"）：正确答案是"语料里没有"，不存在应该被
  召回的片段，检索指标对它无意义——它考的是生成阶段会不会编。
- **"韩立是谁"**：「韩立」出现在 15536 个片段里，随便召回都命中，指标恒为满分、
  区分不出好坏。

### 实测基线（改进开始之前）

```

recall@3     0.455
recall@5     0.727
recall@10    0.727
recall@20    0.818
MRR          0.478

```

**这个基线立刻暴露了三个真实问题**：

| 用例 | 现象 | 说明 |
| --- | --- | --- |
| Q3「韩立的家里都有谁」 | 完全未命中 | 「韩铸」只出现 4 次，被淹没了 |

注意 `recall@5 = 0.727` 和 `recall@20 = 0.818` 的差距：有一条用例的正确片段
"在候选池里但排不进前 5"。这就是典型的**排序问题而非召回问题**。

## 1. BM25：让关键词检索真正会排序

### 为什么需要它（向量检索补不上的洞）

向量检索靠语义相似度。但有一类东西它天生不可靠：**必须逐字匹配的专有名词**。
语义上「韩铸」和「韩立」极其接近（都是姓韩的人名，同一本书，同一个语境），
但它们是两个人。指望 embedding 区分开是不现实的。

所以需要一条完全不同的召回路径：按词精确匹配。这就是 BM25。

### 改造前的实现有个真问题

改造前的"关键词检索"是这样的：

```sql
WHERE position(词 in 正文) > 0 ORDER BY chunk_id LIMIT 20
```

`ORDER BY chunk_id` 意味着**按片段在书里的先后顺序取前 20 个，完全没有相关性排序**。
实测确认：

```
查询「韩立的师父是谁」→ 召回 chunk_id: [357, 358, 1456, ..., 10123]
《凡人修仙传》共 19501 个片段，召回的最大 id = 10123
```

**后半本书对关键词检索完全不可见**——只要某个词命中超过 20 个片段，永远只能
拿到最靠前的那些。

更糟的是这个无序列表接着喂给了 RRF 融合，而 RRF 的前提是**每一路输入都已经
按相关性排好序**。等于给 RRF 喂了噪声。

### BM25 公式，逐项拆解

```
score(D, Q) = Σ  IDF(t) · ────────tf · (k1 + 1)────────
             t∈Q            tf + k1 · (1 - b + b · |D|/avgdl)
```

三个部分各解决一个问题：

**① IDF(t) = ln((N - df + 0.5) / (df + 0.5) + 1) —— 词的区分度**

`df` 是"这个词出现在多少个片段里"。实测本项目的数据：

| 词 | df | IDF | 含义 |
| --- | --- | --- | --- |
| 韩立 | 15435 | 0.75 | 到处都是，几乎不携带信息 |
| 绰号 | 36 | 6.80 | 罕见，出现即强信号 |

**这一项直接取代了改造前那个手写的启发式**（"命中超过 300 个片段的词就整个
丢掉"）。IDF 做的是同一件事，但是**平滑降权**而不是**硬性丢弃**——常见词仍然
贡献一点分数，只是很少。这更合理：一个词常见不代表它没用，只代表它不该单独
决定排序。

**② tf 项 —— 词频，但边际递减**

一个片段里出现 10 次「南宫婉」比出现 1 次更可能真的在讲她，但相关性不是 10 倍。
`k1`（默认 1.2）控制饱和速度：tf → ∞ 时这一项收敛到 `k1 + 1 = 2.2`。

**③ |D|/avgdl 长度归一化 —— 消除长片段的系统性优势**

长片段天然更容易碰巧包含查询词。不归一化的话最长的片段会在所有查询里都排前面。
`b`（默认 0.75）控制强度：0 = 完全不管长度，1 = 完全按长度比例惩罚。

### 实现：倒排索引 + 在 SQL 里算 BM25

为了让公式**看得见**，这里没有用现成的搜索引擎，而是自己建倒排索引：

```sql
CREATE TABLE chunk_terms (
    novel TEXT, chunk_id INTEGER,
    term TEXT,
    tf INTEGER,        -- 这个词在这个片段里出现几次
    PRIMARY KEY (novel, chunk_id, term)
);
```

全库 32730 个片段 → **385 万行**倒排索引，建索引耗时约 3 分钟（含向量化）。
写入用 `COPY` 而不是 `executemany`——后者要为每行走一次完整的 SQL 往返，
几百万行会慢到不可接受。

打分的 SQL 里，三项公式逐项对应写出来了，见
[`src/rag.py`](../src/rag.py) 的 `keyword_retrieve`。

### 踩到的坑：书名不该当内容词

第一版实测跑出来**有的用例反而变差**（Q1 从 #2 掉到 #14）。查出来是个真 bug：

用户问「**《凡人修仙传》**里，韩立小时候的绰号是什么」，书名被 jieba 切成
`凡人` + `修仙`，当成**内容词**参与了打分：

```
【BM25 第 1 名】总分 17.63          【目标片段】总分 10.13
   凡人  tf=5 idf=4.40 → 7.73          韩立  tf=3 idf=0.75 → 1.22
   修仙  tf=8 idf=3.37 → 6.40          绰号  tf=1 idf=6.80 → 7.24  ← 真正的关键词
   韩立  tf=6 idf=0.75 → 1.37          这个  tf=1 idf=1.57 → 1.67
   这个  tf=2 idf=1.57 → 2.12
```

书名两个词白送了 14.1 分，把正确答案压了下去。

**根本原因**：书名的职责是**路由**——确定在哪本书里搜。一旦已经靠它把范围限定到
《凡人修仙传》，再拿「凡人」「修仙」去这本书内部做关键词匹配就是纯噪声，整本书
都在讲凡人修仙。

修法是 BM25 检索前把已识别的书名从问题里剥掉（`_strip_novel_titles`）。
**注意只对 BM25 这一路做**：语义检索编码的是整句话的含义，书名只是让语义更完整
的上下文，不会像 BM25 那样被拆成独立的词各自累加。

顺带发现 `这个` 也漏进了查询词（df=6807，纯噪声）——jieba 把「这个」切成一个词，
光在停用词表里放「这」「那」拦不住。

### 实测效果

| 指标 | 基线 | BM25 后 | 变化 |
| --- | --- | --- | --- |
| recall@1 | 0.364 | 0.455 | **+0.091** |
| recall@3 | 0.455 | **0.727** | **+0.272** |
| recall@5 | 0.727 | 0.727 | — |
| recall@10 | 0.727 | 0.818 | +0.091 |
| MRR | 0.478 | **0.589** | **+0.111** |
| 平均耗时 | 949ms | **261ms** | **快 3.6 倍** |

最能说明问题的单条：**Q2「窝头」（全书只出现 1 次）从第 19 名冲到第 1 名**。
这正是 IDF 该有的效果——极稀有的词一旦命中就是决定性证据。

变快 3.6 倍是意外收获：改造前每个候选词都要单独跑一次 `COUNT` 全表扫描，
现在是一条 SQL 走倒排索引。

**仍然存在的问题**（如实记录，不粉饰）：

- Q14「韩立修炼的功法叫什么」从 #4 退到 #7，仍在 top-10 内但排序变差了。
- Q3「韩立的家里都有谁」、Q6「谁的绰号叫二愣子」依然完全未命中。

这几条的共同点是**问题里的词和答案原文里的词对不上**（问"家里都有谁"，原文
写的是具体人名「韩铸」）。BM25 是词袋模型，天生处理不了这种"问法和答法用词
不同"的情况——这正是下一步[重排](#2-重排reranker)和
[Contextual Retrieval](#3-contextual-retrieval)要解决的。

[`src/ingest.py`](../src/ingest.py)（建倒排索引）、

## 2. 重排（reranker）：双编码器 vs 交叉编码器

### 为什么需要它

[BM25 那一节](#1-bm25让关键词检索真正会排序)结束时留了三个没解决的用例：

- Q14「韩立修炼的功法叫什么」排在 #7
- Q3「韩立的家里都有谁」、Q6「谁的绰号叫二愣子」完全未命中

共同点是**问法和答法用词不同**：问"家里都有谁"，原文写的是具体人名「韩铸」。
BM25 是词袋模型，只会数词的匹配，天生处理不了这个。向量检索能懂一点语义，
但它精度有限——原因就在下面。

### 核心：两种模型的架构差异

这是检索系统里最重要的一个权衡，值得画出来看：

**双编码器（bi-encoder）—— 本项目 `embedder.py` 用的**

```
问题 ──→ [编码器] ──→ 向量 A  ┐
                               ├─→ 算余弦相似度
文档 ──→ [编码器] ──→ 向量 B  ┘
```

问题和文档**各自独立**编码，编码完了才做一次简单的向量比较。

- ✅ 文档向量能**预先算好存起来**（本项目 32730 个片段的向量都存在
  `novel_chunks.embedding` 里）。查询时只需编码问题这一次，剩下是纯向量运算，
  几万个片段几毫秒扫完。
- ❌ 精度有限。**编码文档的时候根本不知道用户会问什么**，只能把整段文本压成
  一个固定长度的向量，压缩过程必然丢信息。

**交叉编码器（cross-encoder）—— 本项目 `reranker.py` 用的**

```
[问题 + 文档] 拼在一起 ──→ [编码器] ──→ 相关性分数
```

两者**拼成一段**送进模型，内部的注意力机制让问题里的每个词能和文档里的每个词
直接交互——「绰号」这个词可以直接"看到"文档里的「二愣子」。

- ✅ 精度高得多。能判断"这段话是不是真的在回答这个问题"，而不只是
  "主题相近"。
- ❌ **没法预计算**。每换一个问题，所有文档都要重算。对 32730 个片段跑一遍
  要几分钟，完全不可能用来做全库检索。

### 所以标准做法是两阶段

```
32730 个片段
    ↓  双编码器 + BM25（快，粗）
   60 个候选          ← 召回阶段：宁可多召回，别漏
    ↓  交叉编码器（慢，精）
   20 个结果          ← 重排阶段：从候选里精挑
```

只对几十个候选跑交叉编码器，耗时可以接受。

**关键认知：重排只能改善排序，救不回没召回到的东西。** 如果正确答案根本不在
候选池里，重排也无能为力。所以：

- `Recall@20` 不变、`MRR` 上升 → 重排在正常工作（把对的往前挪）
- `Recall@20` 也上升 → 那是候选池扩大带来的，不是重排的功劳

评测时要把这两种效果分开看，不能混为一谈邀功。

### 实现要点

**① 候选池必须大于最终结果，重排才有得挑**

踩过的坑：第一版写成 `if len(candidates) > top_k` 才重排，而候选池
`candidate_k = max(top_k, RECALL_K)`。评测时 `top_k=20`、`RECALL_K=20`，
于是 `20 > 20` 为假——**重排被整个跳过，评测等于测了个寂寞**。

修法是让候选池按倍数放大：`candidate_k = max(top_k × 3, RECALL_K)`。
业界经验是「召回 20 → 重排到 5」这个量级，即 3~4 倍。

**② 重排失败不能让问答挂掉**

模型 1.1GB，可能下载失败、加载失败、推理出错。这些都不该让整个问答不可用——
`try/except` 兜住，退回融合排序的结果（质量差一点，但功能可用）。
`RERANK_ENABLED=0` 可以完全关掉。

**代码**：[`src/reranker.py`](../src/reranker.py)、
[`src/rag.py`](../src/rag.py) 的 `retrieve_hybrid_traced` 阶段五

**必须如实说明**：这台机器的网络无法稳定下载 `bge-reranker-base`（1.1GB）——

## 3. Contextual Retrieval：成本才是主要矛盾

### 为什么需要它

片段被切开后就失去了上下文。本项目里的真实例子——《降龙》某个片段原文是：

> "候不同，有打斗的痕迹。**他们**既然来过，又数日未回，或许是出了什么意外？"
> "四哥，我前日起卦，卦象大凶！就怕**八弟他们**......"

通篇「他们」「八弟」「四哥」，**没有任何一个人物本名**。你问"柳崖村的人在徐猛家
发现了什么"，这段话既匹配不上「徐猛」也匹配不上「柳崖村」——正确答案就在眼前
却召回不到。

### 做法

入库前用 LLM 给这类片段生成一句定位说明，拼在前面再做 embedding 和 BM25 索引：

```
索引的是：  "王慎与顾思盈分别后，柳崖村的两兄弟发现徐猛家中有打斗痕迹…" + 原片段
回答用的是： 原片段（不把生成的说明混进正文）
```

### 但直接照搬原始方案会撞墙

Anthropic 的做法是把**整篇文档**连同片段一起发给 LLM，靠 prompt caching 摊薄成本
（[官方数字 $1.02/百万文档 token](https://www.anthropic.com/engineering/contextual-retrieval)）。
那套算法的前提是**文档是 8K token 量级**的技术文档、财报、法律文件。

本项目完全不成立：

```
《凡人修仙传》903 万字 ≈ 600 万 token
GLM-4-Flash 上下文窗口   12.8 万 token      ← 差 47 倍
```

**整本小说根本塞不进上下文**，prompt caching 无从谈起。只能退而求其次，用片段
前后各 2 段当"文档"——效果比原方法差（模型看不到全书的人物关系），但这是长篇
小说场景下唯一可行的做法。

### 成本实测

| 项目 | 实测值 |
| --- | --- |
| 单次 LLM 调用（GLM-4-Flash） | **4.4 秒** |
| 全库 32730 个片段串行 | **40 小时** |
| 10 路并发 | 4 小时 |
| 对比：当前重建索引全流程 | **3 分钟** |

**所以成本控制不是可选项，是这个技术能不能用的前提。** 这里做了三道闸门：

**闸门 1：按书跳过**（`CONTEXTUAL_MAX_CHUNKS_PER_BOOK=2000`）

超过阈值的书直接不做。默认值刻意卡在《降龙》(1278) 之上、《诡秘之主》(11948) 之下，
避免手一滑跑一整夜。

**闸门 2：只处理真正缺上下文的片段**

判据：**有指代性词语（他/她/他们/那汉子…），但不含任何主要人物名**。
人物名用 jieba 的 `nr` 词性标注按频次提取。

实测《降龙》1278 个片段里只有 **451 个（35.3%）**命中——直接省掉三分之二的调用。

> 踩过的坑：提取人物名的频次门槛一开始写死为 20。结果只有 3 个片段的
> 《雾隐山庄》里没有任何名字能出现 20 次，名单成了空集合，于是"不含任何人物名"
> **恒为真**——所有片段都被误判成缺上下文，判据在小书上静默失效。
> 改成按片段数取比例（`max(2, len//50)`）后修复。

**闸门 3：增量复用**

生成结果按**片段原文的哈希**存进独立的 `chunk_contexts` 表（不跟着 `recreate_schema`
被删）。实测第二次重建：**451 条全部命中缓存，0 次 LLM 调用，10 秒**（首次约 4 分钟）。

> 用内容哈希而不是 `(书名, chunk_id)` 做键：切分参数一变，同一个 chunk_id 对应的
> 文本就变了，用位置做键会取到过期的上下文。内容哈希天然正确——文本没变就复用，
> 变了自然查不到、会重新生成。

### 实测效果（A/B 对比）

专门加了两条用例，问题里用的关键词**只出现在生成的说明里、原文片段里完全没有**：

| 用例 | 有增强 | 无增强 |
| --- | --- | --- |
| Q17「柳崖村的人在徐猛家发现了什么」 | **#2** | #9 |
| Q18「王慎在铁匠铺遇到谁在骚扰邻居」 | **#5** | **未命中** |

整体指标（13 条可自动判定的用例）：

| 指标 | 有增强 | 无增强 | 差值 |
| --- | --- | --- | --- |
| recall@5 | **0.769** | 0.615 | **+0.154** |
| recall@20 | **0.846** | 0.769 | +0.077 |
| MRR | **0.552** | 0.507 | +0.045 |

Q18 最能说明问题：**不做增强就完全召回不到**——原文里只有「那汉子」，
`王慎`、`铁匠铺` 这些词一个都没有。

### 又一个坑：优雅降级不能把原因也吞掉

第一次跑完，日志只有一句「451 条生成失败」，**看不出任何原因**。真实原因是
`ingest.py` 独立运行时不走 FastAPI 的 lifespan、没加载 `.env`、拿不到 API key。

生成失败降级为"索引原文"是对的（不该让整个入库流程卡住），但**只报个数字不报
原因，等于让人自己去复现才能排查**。修法是把异常收集起来由调用方汇总打印。

这是个通用教训：**降级路径也要可观测**。

### 什么时候值得用

从上面的成本可以看出，Contextual Retrieval 是**为单篇几千到几万 token 的文档**
设计的（技术文档、财报、法律文件），不是为百万字长篇小说设计的。

生产环境的正确用法是：
- **入库时一次性生成**（不是查询时——查询时生成在逻辑上就做不到，见下）
- 用**便宜的小模型**（Anthropic 官方用 Haiku，本项目用 GLM-4-Flash）
- **只对重要文档**做
- 配合 **prompt caching**（如果文档能塞进上下文窗口）

> **为什么不能"查询时再生成"**：这不是成本权衡，是逻辑上不可能。context 的作用
> 是**改变这个片段能被什么样的查询命中**——它必须先被 embedding 编码、先写进
> 倒排索引，才能影响检索结果。等检索完了再加 context，检索已经发生了。

### 替代方案：Late Chunking

同一个问题的另一种解法，**便宜得多**：先把整篇文档过一遍 transformer 拿到每个
token 的向量（此时每个 token 都"见过"全文了），**然后**才按片段边界做 mean pooling。
"晚"指的就是池化推后了。

| | Contextual Retrieval | Late Chunking |
| --- | --- | --- |
| 怎么补上下文 | LLM **生成**一段文字 | embedding 模型**先编码整篇再池化** |
| 需要什么 | LLM 调用 × 片段数 | 只要 embedding 模型，**零 LLM 调用** |
| 本项目成本 | 40 小时 | 与现在重建索引相当（分钟级） |

**但对本项目有硬门槛**：Late Chunking 需要长上下文 embedding 模型（8K token 量级），
而当前的 `bge-small-zh-v1.5` 上限是 **512 token**。要用得换模型 + 重建全库索引。

## 4. 多轮查询改写：检索发生在生成之前

### 为什么需要它

这个项目的 prompt 一直是**完全无状态**的：每次提问只把检索到的片段和当前问题
拼给模型。历史对话虽然从 PR #16 起就存在 `chat_turns` 表里，但**从来没有参与
过检索**。

于是这样的对话必然失败：

```
用户：韩立的师父是谁？
助手：韩立的师父是李化元。
用户：他后来怎么样了？        ← 拿这七个字去检索，什么也搜不到
```

### 核心认知：为什么不能指望生成模型解决

一个很自然的想法是"把历史也塞进 prompt，让模型自己理解「他」是谁"。这解决不了
问题，因为**检索发生在生成之前**：

```
用户提问 → 【检索】→ 拿到片段 → 【生成】→ 回答
              ↑
    "他"在这一步就必须已经被解析成"李化元"
    否则检索到的是一堆无关片段，生成模型再聪明也无米下炊
```

所以必须在检索**之前**把问题补全：

```
"他后来怎么样了"  ──改写──→  "李化元后来怎么样了"  ──→ 检索
```

### 为什么不直接把历史拼进检索查询

最省事的做法是把最近几轮对话原样拼在问题前面一起做 embedding。但那样会把大量
无关内容混进查询向量——上一轮的完整回答可能几百字，会把「他后来怎么样了」这句
真正的问题稀释掉，检索结果反而更差。

改写成一句独立完整的问题，既解决了指代，又不引入噪声。

### 成本控制：不是每次追问都要改写

改写要多调一次 LLM，会给**每一次追问**都加延迟。所以设了两道门：

1. **第一轮不改写**——没有历史，没有指代可解析
2. **看起来自足的问题跳过**——不含指代词（他/她/这/那/后来/然后…）且长度
   超过 8 个字时，直接用原问题

用的是便宜的小模型（`glm-4-flash`），**且刻意不复用当前对话选的模型**——
用户可能选了推理型的大模型，那样改写会白等好几秒。

### 实测

```
第 1 轮：韩立的师父是谁？        → 李化元
第 2 轮：他后来怎么样了？
        后端日志：查询改写：「他后来怎么样了？」→「李化元后来怎么样了？」
        界面「思考过程」第一步：补全指代后按「李化元后来怎么样了？」检索
```

改写这一步会显示在「思考过程」里——它是个**会改变检索结果的隐式步骤**，
藏起来的话用户无法理解"为什么搜出了这些"。

### 踩的坑：误触发比不触发更糟

第一版长度阈值设成 12，结果问「雾隐山庄的庄主得了什么病」（正好 12 个字、
本来就自足）也触发了改写。模型只把「的」去掉，返回「雾隐山庄庄主得了什么病」
——字符串不同，于是界面上显示"补全指代后按…检索"。

**用户根本没写任何指代，这个提示纯属误导**，还白花了一次 LLM 调用。

修了两处：
- 阈值降到 8
- **改写结果和原问题实质相同时当作没改**（去掉标点和虚词后比较）。
  这条更根本——阈值怎么调都会有边界情况，而这个判断能兜住所有"改了等于没改"
  的场景。

另外还挡了两种坏改写，它们比不改写更糟（会把检索引到错误方向）：
- 模型返回空串
- 模型啰嗦一大段解释而不是一个问题（按长度暴涨判断）

[`backend/main.py`](../backend/main.py) 的 `_rewrite_for_search`

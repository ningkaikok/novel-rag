# 检索可视化评测闭环

最终答案错误时，只看三张出处卡片无法知道问题出在哪。现在每次原文问答都会记录并
展示四个关键排名阶段：

| 阶段 | 分数 | 主要回答的问题 |
| --- | --- | --- |
| 向量召回 | 余弦相似度 | 语义粗筛有没有找到正确片段 |
| BM25 召回 | BM25 分数 | 人名、专有名词这一路有没有找到 |
| RRF | 融合分数 | 多路合并后正确片段排到哪里 |
| 重排 | CrossEncoder 分数 | 精排把它提升了还是错误压低了 |

全局问题还会多一个“层级检索”阶段，结构性问题会多一个“原文位置”阶段。

## 界面怎么看

回答下方打开“📊 检索评测”。每个阶段最多显示前 10 个候选：

- `#N` 是该阶段名次；
- “上一阶段”显示重排前后的变化，例如 `#8 → #2`；
- 高亮行是最终会进入上下文的候选；
- 阶段标题旁是耗时，可直接发现瓶颈是在数据库召回还是本地精排。

一个实用排查顺序：

1. 正确片段在向量/BM25 都没有出现：召回问题，检查切分、查询词或 embedding。
2. 粗召回出现但 RRF 后掉出候选：融合或候选预算问题。
3. RRF 很靠前、重排后掉下去：检查 CrossEncoder、上下文增强文本和问题表达。
4. 最终来源正确但答案错误：进入生成/提示词层，不要继续盲目调检索。

## 协议与存储

`TraceStep` 增加稳定的 `stage_key` 和轻量 `candidates`。候选只保存书名、片段号、章节、
名次和分数，不重复保存大段原文；原文仍只在最终 `sources` 中发送。普通会话落库时 trace
会随回答保存，刷新页面后仍可复盘。

后端回归测试 `tests/backend/test_retrieval_trace.py` 会固定构造一次排名变化，验证四层
数据都存在且 `previous_rank/selected` 正确；前端 E2E 会展开面板验证真实交互。

注意：这个面板是单次问答的“调试显微镜”，不是数据集级指标。比较算法版本仍要运行
`scripts/eval_retrieval.py --compare ...`，两者配合才构成完整闭环。

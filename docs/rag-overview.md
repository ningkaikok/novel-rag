# RAG 学习总览：四个杠杆，和一路踩过的坑

这份是**入口文档**。想看某个技术的完整推导和代码，去
[rag-techniques.md](rag-techniques.md)；这里只做三件事：

1. 把整条链路串起来，说清楚每个环节在解决什么
2. 把所有实测数据放进一张表，包括**没有效果的那些**
3. 记录方法论层面的教训——这部分比技术本身更通用

---

## 一、本项目的核心判断：先解决检索，再优化生成

模型只能依据送进上下文的内容作答。项目里的多次失败案例都说明：如果正确原文没有
进入候选集，换更强的生成模型也救不回来；所以这里先把主要精力放在可测量的检索侧。
这是一条由本项目评测支持的工程判断，不把缺少可核验来源的行业百分比当作结论。

所以调优的重点在检索侧，具体是四个杠杆：

| 杠杆 | 解决什么 | 本项目的实现 |
| --- | --- | --- |
| **切分** | 一段里塞太多内容 → 向量被稀释；切太碎 → 上下文断裂 | 按标点切 + 邻居扩展 + Contextual Retrieval |
| **混合检索** | 向量懂语义但记不住生僻词；关键词记得住但不懂语义 | 向量 + BM25 双路召回，RRF 融合 |
| **重排** | 召回阶段为了快，用的是精度较低的模型 | 交叉编码器对候选做二次精排 |
| **长上下文取舍** | 送得多≠答得好，还更贵更慢 | 实测 TOP_K，最终定 3 |

这四个杠杆本项目**都实现了**，而且每一个都有前后对比数据。

## 二、一条问题走完的完整链路

```
用户提问
   │
   ├─ ① 回答路径 ────────  开放问题直接回答；小说问题进入原文链路
   │      └─ 自由问答 ───  跳过下面的检索，不伪造出处
   │
   ├─ ② 多轮改写 ────────  "他后来怎么样了？" → "李化元后来怎么样了？"
   │   （只在有历史+疑似指代时触发）   ↑ 必须在检索之前做，指代没消解检索必错
   │
   ├─ ③ 书名路由 ────────  识别《凡人修仙传》，把检索范围限定到这本书
   │       │                （容错：打错字也能匹配上）
   │       │
   │       └─ 小书短路 ──  全文 < 8000 字？直接把全书塞进去，跳过检索
   │
   ├─ ④ 多路召回（当前按顺序执行）
   │      ├─ 层级检索  ──  全局问题先搜全书/章节摘要，再回到原文
   │      ├─ 向量检索  ──  pgvector HNSW，懂语义
   │      ├─ BM25      ──  自建倒排索引，记得住「窝头」这种只出现 1 次的词
   │      └─ 结构检索  ──  问开头/结局时按 chunk_id 定位，语义相似度不适用
   │              │
   │              └─ RRF 融合 ── 1/(k+rank)，k=60，只看排名不看分数
   │
   ├─ ⑤ 交叉编码器重排 ──  取 TOP_K×3 个候选，逐个和问题一起过模型
   │       │                ⚠️ 必须送 context+text，送裸 text 会毁掉 ③ 的成果
   │       │
   │       └─ 邻居扩展 ──  命中片段的前后各取一段，补回被切断的上下文
   │
   ├─ ⑥ 图线索（默认关闭）─ 关系类问题查预建的人物关系图
   │
   └─ ⑦ 来源统一编号 → 拼 prompt → 流式生成 → 前端边收边渲染（可中断）
          └─ 回答中的 [n] 可定位到书名、章节和原文片段
```

对应代码：[rag.py](../src/rag.py) 是主干，
[code-walkthrough.md](code-walkthrough.md) 逐行讲了每个函数。
问答路径的规则、覆盖方式和离线评测见 [answer-routing.md](answer-routing.md)。
章节切分、来源编号不变式和引用评测见
[citations-and-chapters.md](citations-and-chapters.md)。

这张标准 RAG 流程图看起来像“图”，但当前不需要 LangGraph，因为它仍是固定的数据
处理流水线。独立的 Agent Lab 虽会自主选择五个只读工具，但最多五步、无需恢复，普通
Python 循环更适合学习。详细判断见[架构决策](architecture-decisions.md)和
[Agent Lab](agent-lab.md)。另外，本文的 GraphRAG 指“人物关系图检索”，和用于编排
Agent 工作流的 LangGraph 不是同一个概念。

## 三、所有实测数据（含负面结果）

评测集 13 题，覆盖三本书。指标定义和跑法见
[rag-techniques.md 第 0 节](rag-techniques.md)。

| 阶段 | recall@1 | recall@3 | recall@5 | MRR | 平均耗时 |
| --- | --- | --- | --- | --- | --- |
| 起点（子串匹配当关键词检索） | 0.364 | 0.455 | 0.727 | 0.478 | 837ms |
| ＋ BM25 | 0.455 | **0.727** | 0.727 | 0.589 | **379ms** |
| ＋ Contextual Retrieval ※ | 0.385 | 0.692 | **0.769** | 0.552 | 217ms |
| ＋ 交叉编码器重排 | **0.692** | **0.846** | **0.846** | **0.744** | 2339ms |
| ＋ TOP_K 调优（5→3） | 0.615 † | 0.846 | 0.846 | 0.705 | 1971ms |

> ※ **前两行是 11 题，后三行是 13 题**——题集在这一步扩充了，所以
> 第 2 行到第 3 行的数字**不能直接对比**。Contextual Retrieval 的真实效果
> 是用同题集 A/B 测的：recall@5 **0.769 vs 0.615**，Q17 排第 2 vs 第 9，
> Q18 命中 vs 完全没召回。
>
> † recall@1 的下降**不是真实回退**。小书走全文短路时，片段按阅读顺序返回、
> 且全部进 prompt，"排第几"这个指标在这种模式下没有意义。已在
> [eval_retrieval.py](../scripts/eval_retrieval.py) 里注明这个局限。

### 单点上的显著案例

| | 变化 |
| --- | --- |
| Q2「窝头」（全书只出现 1 次） | 第 19 名 → **第 1 名**（BM25） |
| Q18 | 完全没召回 → **第 1 名**（修好重排的输入之后） |
| BM25 替换子串匹配 | 速度 **快 3.6 倍**（子串匹配要全表扫） |
| TOP_K 5→3 | prompt **省 39% 字符**，召回一点没掉 |

最后一条值得单独说：**重排真正的价值不是"排得更准"，是"让你可以少送"。**
排得准了，前 3 条就够，不用靠堆数量来碰运气。

### 负面结果

| 技术 | 结果 |
| --- | --- |
| **GraphRAG** | 原理跑通、130 条边建好，但共现推断精度不够（把师父、男性角色都算成伴侣），端到端模型拒答，**净收益为零**。默认关闭，详见[第 6 节](rag-techniques.md) |
| **jieba 词性标注抽人名** | 完全不可用。复姓被切成地名、三字名被切开，top-40 里**一个真人名都没有** |
| **Late Chunking** | 没做。需要 8K 上下文的 embedding 模型，本项目的 `bge-small-zh-v1.5` 上限 512 |

## 四、方法论教训（这部分最通用）

技术会过时，下面这些不会。每一条都是这个项目里**真实踩出来的**。

### 1. 静默降级不能把原因也吞掉

Contextual Retrieval 第一次跑，451 条全部生成失败，日志只写了
「451 条生成失败」。根因是脚本没加载 `.env`，但从日志里完全看不出来。

> 降级是对的——一批失败不该让整个流程崩。
> **但降级必须留下"为什么"**，否则你只知道坏了，不知道坏在哪。

修复不只是补上 `.env`，还把错误收集进 `errors` 列表打印出来。
后来 `graph.py` 里的抽取失败处理直接沿用了这个模式。

### 2. 同一个函数，在不同精度要求下不能盲目复用

建图时想直接用 `contextualizer.extract_main_characters()` 抽人名。
那个函数对它自己的用途（判断"这段里有没有人名"）够用了，但**建图需要准确的
人名**——抽错一个名字，会顺带生成一大片错误的边。

> 复用前先问：**新场景对精度的要求，和原场景一样吗？**

### 3. 指标下降不一定是回退

TOP_K 调优后 recall@1 掉了 0.077,第一反应是"改坏了"。查下来发现是小书走了
全文短路——那种模式下所有片段都进 prompt，"排第几"根本没意义，而且按阅读
顺序给模型反而更好。

> **先搞清楚指标在这个场景下还成不成立**，再判断是不是回退。

### 4. 采样方式比模型选择更重要

抽人名时，全书均匀采样 60 段（覆盖 0.3%）怎么都抽不到南宫婉。
换成**只采含关系词的片段**，11 次调用就抽全了，还更省。

> 换更强的模型是最贵也最偷懒的优化。
> 先看**喂进去的数据对不对**。

### 5. 改了实现，注释和文档要跟着改

`postgres.py` 里有一句注释写着"纯规则抽取，重建只要几秒，没有复用的必要"——
写在改用 LLM 抽取**之前**，改完之后它就成了假的。

这个是用户问「文档和注释有同步更新吗」才发现的。讽刺的是，我刚在文档里
写完这条教训。

> **陈旧的注释比没有注释更有害**，它会让人基于错误前提做决定。

### 6. 上游改了，下游的输入也得跟着改

Contextual Retrieval 给每个片段加了 context，索引侧用上了，
**但重排侧还在送裸 text**。同一个片段，重排模型给出的分数是
**0.0055 vs 0.9990——差 180 倍**。等于前一个技术白做了。

> 加了新字段之后，**把所有消费这个数据的地方都过一遍**。

### 7. 先建评测，再动手改

这是第 0 节而不是最后一节，是有原因的。没有评测的时候，
"感觉变好了"和"真的变好了"分不开——上面那些"以为改好了其实改坏了"
的坑，**没有一个是靠肉眼看出来的**。

### 8. "检索有效"这个结论本身要小心被模型的记忆污染

拿热门公开小说测出"给了检索内容答案就变对"，不能直接当成"检索系统有效"的证据——
模型很可能**背过**这部小说，答对可能纯粹是记忆，跟你喂的那段文字毫无关系。
测试对象本身有没有可能污染结论，要在设计阶段就想到，不能等结果出来再怀疑。

> 用模型训练数据里**保证没有**的语料（比如项目自己原创的短篇）先验证一次，
> 再用**篡改关键事实**的手法在热门语料上验证一次——如果模型跟着篡改后的假信息走，
> 才能证明它这次真的在依据你给的文本，不是在表演。完整方法和数据见
> [grounding-verification.md](grounding-verification.md)。
